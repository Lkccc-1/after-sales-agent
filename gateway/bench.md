# 网关压测记录

- 日期：2026-11-10
- 环境：Windows 11 Pro / Docker Desktop 29.9.2 / Dify 1.19.0 单机容器 / 模型 `deepseek-flash`（经 Dify deepseek 插件）
- 被测服务：`gateway/main.py`（uvicorn 单进程，127.0.0.1:8000）
- 请求：100 次，并发 20，问题固定为「七天无理由退货有什么条件？」（政策类，走知识检索）
- 原始数据：`bench_result.json`；请求日志：`logs/gateway.jsonl`

## 结果

| 指标 | 结果 |
|---|---|
| 成功 | 100 / 100 |
| 错误率 | 0% |
| p50 | 14,110 ms |
| p95 | 18,235 ms |
| max | 21,577 ms |
| 并发 | 20 |

**单请求基线**：同一问题串行调用，经网关端到端约 6.9–8.2 s（见 `logs/gateway.jsonl` 中非压测的 `ok` 行）。

## 结论

1. **20 并发下 p50 从 ~7.6 s 升到 14.1 s，p95 18.2 s，约为单请求基线的 2 倍**；100 次全部成功、错误率 0%，说明瓶颈是**模型调用排队**，不是网关丢请求或超时。
2. **网关自身开销无法从端到端延迟中可靠分离**。直连 Dify 与经网关各 6 次交替测试（`direct_result.json`）：直连中位数 7,596 ms，经网关 9,092 ms，差 1,496 ms；但两组样本的离散度（直连 6,249–9,147 ms，网关 6,589–13,860 ms）大于该差值，差异被模型侧波动淹没。网关每次请求只做一次 JSON 序列化和一行日志写入，静态开销可忽略。**因此不写「网关开销 = 1.5 s」这种假精确数字。**
3. 若上生产：瓶颈在模型调用侧，需要**模型侧限流 + 队列**，或水平扩 Dify worker；单机 Docker（Windows + WSL2）只适合演示与本机压测，结论仅在这个口径内成立。
4. 100 次压测共消耗约 23 万 tokens（每次约 2,300，取自日志 `tokens` 字段），成本可忽略，但说明**压测要控制样本量**。

## 复现

```bash
# 1. 启动网关
uvicorn gateway.main:app --host 127.0.0.1 --port 8000
# 2. 压测
python gateway/bench.py
# 3. 直连 vs 网关对照
python gateway/bench_direct.py
```
